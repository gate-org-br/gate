Delete

Delete flows should be explicit about scope and outcome. The best production patterns combine strict predicates and row-count validation.

Delete By ID

Canonical delete with typed ID.

Delete.from("Attachment")
	.where(Condition.of("id").eq(ID.class, value.getId()))
	.build()
	.connect(getLink())
	.execute();

Why this is useful:

  • Precise and auditable deletion target
  • Simple to reason about and test
  • Avoids accidental broad deletes
Delete + Not Found Guard

Preferred API behavior when deleting a required record.

if (Delete.from("Organization")
	.where(Condition.of("id").eq(value.getId()))
	.build()
	.connect(getLink())
	.execute() == 0)
	throw new NotFoundException();

Why this is useful:

  • No silent failures
  • Caller receives clear status semantics
  • Supports optimistic concurrency checks
Delete with Subquery Predicate

Useful when deletion key is discovered through relational lookup.

Delete.from("Attachment")
	.where(Condition.of("Attachment.id")
		.isEq(Select.expression("Category.Attachment$id")
			.from("Category")
			.where(Condition.of("Category.id").eq(category.getId()))))
	.build()
	.connect(getLink())
	.execute();

Why this is useful:

  • Encodes relationship rule in one SQL operation
  • Avoids extra select-then-delete roundtrip
  • Keeps cleanup logic consistent with relational model
Full Table Delete (Administrative)

Only for controlled maintenance flows.

Delete.from("Device")
	.build()
	.connect(getLink())
	.execute();

Important:

  • Use only in explicit admin/maintenance paths
  • Prefer transaction boundaries and audit logs
  • Avoid exposing this in user-facing APIs
