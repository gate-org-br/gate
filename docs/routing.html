Routing

Gate routes web requests from Java structure. Package, screen class and call... methods form the request identity handled by the framework.

Overview

The Screen Model is the backend convention that gives Gate its routing structure. Instead of declaring routes in a separate registry, Gate projects the structure of the Java application into web entry points. A request is resolved from the package of the screen, the screen class itself and the selected call... method.

This means the route model is not an extra layer on top of the codebase. It is the codebase. When a developer creates a new screen class, names it according to the framework convention and exposes one or more call... methods, Gate can derive the corresponding MODULE, SCREEN and ACTION identifiers directly from that structure.

The convention is intentionally compact:

  • Package name becomes MODULE.
  • A class ending with Screen becomes a routable SCREEN.
  • call() is the main action of the screen.
  • callSelect() becomes ACTION=Select.
  • @AllowMethod restricts which HTTP verbs may execute a resolved action.
  • Only CDI-discovered screen beans are registered.

Here are concrete examples of how a request maps to Java code:

Request URL Resolved method
/Gate?MODULE=linq.modulos.gerencia&SCREEN=Area linq.modulos.gerencia.AreaScreen.call()
/Gate?MODULE=linq.modulos.gerencia&SCREEN=Area&ACTION=Select linq.modulos.gerencia.AreaScreen.callSelect()
/Gate?MODULE=linq.modulos.callCenter&SCREEN=Operador.Fila linq.modulos.callCenter.OperadorScreen.FilaScreen.call()
/Gate?MODULE=linq.modulos.callCenter&SCREEN=Operador.Fila&ACTION=Insert linq.modulos.callCenter.OperadorScreen.FilaScreen.callInsert()

In practice, the developer mental model is: create a screen bean, keep the Screen suffix, expose call... methods, and delegate business rules to controls. Gate uses that structure to build the effective application model at bootstrap time.

A screen is exposed only if CDI discovers it and Gate receives it as a Screen bean. For Quarkus applications this usually means the class must be a CDI bean, commonly annotated with @Dependent.

During bootstrap, Gate collects discovered screens, builds the application structure and persists the effective model in the App table. That stored structure represents what was actually registered at runtime.

Nested Screens

When a screen is declared inside another screen class, Gate treats it as a nested route. The nested structure is projected with dot notation.

Java element Resolved value
OperadorScreen.FilaScreen SCREEN=Operador.Fila
CallCenterScreen.UsuarioScreen.PermissaoScreen SCREEN=CallCenter.Usuario.Permissao

Nested screens are useful when a flow is structurally dependent on another screen and should remain grouped in the same Java type hierarchy.

HTTP Methods

Gate does not use HTTP verbs to choose the action. Routing is still based on MODULE, SCREEN and ACTION. HTTP verbs only restrict which requests are allowed to execute a resolved action. 

import gate.annotation.AllowMethod;

@AllowMethod(AllowMethod.HttpMethod.GET)
public Object callSelect() { ... }

@AllowMethod(AllowMethod.HttpMethod.POST)
public Object callInsert() { ... }
