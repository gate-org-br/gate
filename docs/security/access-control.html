Access Control

Gate has its own authorization model. Instead of relying on a flat list of permissions attached directly to the user, Gate computes effective access from multiple sources. Some accesses are shared by an entire area of the organization, others belong to a function, others come from the user's position in the role hierarchy, and others are granted directly to one user. This makes it possible to move users across logical blocks of the organization without adjusting permissions one user at a time. It also keeps authorization data out of the application code.

Overview

Gate stores authorization data in its own database instead of hard-coding access rules in the application. Most routes use the default authorization mode, Security.Type.AUTHORIZATION. In this mode, Gate resolves the request to module, screen and action, then computes whether the current user has effective access to that location.

Auth

An Auth is one access rule. It says whether something is granted or blocked, and to which part of the application that rule applies.

  • Access: GRANT or BLOCK.
  • Scope: PUBLIC or PRIVATE.

GRANT means the auth gives access. BLOCK means the auth denies access. PUBLIC and PRIVATE control inheritance in the role hierarchy. A private auth stays on the role that owns it. A public auth may be inherited through parent roles.

Each auth also has route fields: module, screen and action. These fields define what the rule applies to.

  • If only module is filled, the auth applies to the whole module.
  • If module and screen are filled, it applies to the whole screen.
  • If all three are filled, it applies to one specific action.
  • It may also use partial combinations such as module plus action.

Authorization Sources

A Role is the user's place in the organizational structure. Roles are hierarchical and may carry their own auths and funcs. A Func is a named group of auths that can be attached to users and roles. Together, these concepts allow access to be organized by shared responsibility instead of duplicating permissions user by user.

A User may therefore receive authorization data from several sources:

  • The user's own direct auths.
  • The auths of the funcs attached directly to the user.
  • The auths of the user's role.
  • The auths of the funcs attached to the user's role.
  • Public auths inherited through the role hierarchy.

The user's effective access is computed, not stored in one flat list.

Decision Flow

When a route is executed in the default authorization mode, Gate follows this logic:

  1. Resolve the request to module, screen and action.
  2. Compute the user's effective auths from user, funcs and role.
  3. If any matching auth blocks the route, deny access.
  4. If nothing blocks and at least one matching auth grants the route, allow access.
  5. If there is no matching grant, deny access.

Security Annotations

Gate supports both a general annotation and shortcut annotations.

Annotation Meaning
@Security(Security.Type.NONE) The route is open to everyone
@Security(Security.Type.AUTHENTICATION) The route requires an authenticated user
@Security(Security.Type.AUTHORIZATION) The route uses the normal authorization model
@Security(Security.Type.SPECIFIC_AUTHORIZATION) The route uses the overridden target defined by @Authorization
@Security(Security.Type.SUPERUSER) The route requires a superuser
@Security(Security.Type.BLOCK) The route is blocked for everyone
@Public Shortcut for Security.Type.NONE
@Superuser Shortcut for Security.Type.SUPERUSER
@Disabled Shortcut for Security.Type.BLOCK

These annotations may be declared on the package, on the screen class or on the action method. Method declarations override class declarations, and class declarations override package declarations.

Only one access type may be declared at the same level. For example, declaring @Public together with @Disabled on the same method is invalid. The same is true for mixing a shortcut annotation with @Security(...) on the same element.

Authorization Location Override

@Authorization is different from the other access annotations. It does not define the security type of the route. Instead, it changes which module, screen or action Gate should use during the authorization check.

This is useful when one route should be authorized as if it were another route. The executed action remains the same, but the permission check uses the overridden target.

Gate also supports partial overrides through shortcut annotations:

  • @Module overrides the authorization module.
  • @Screen overrides the authorization screen.
  • @Action overrides the authorization action.

These annotations change only their own coordinate. They are resolved incrementally, starting from the default route location derived from package, screen class and action method. This means the authorization location of the class may be changed at the package level, refined at the class level and changed again for one specific method.

  • @Module on package, class and method.
  • @Screen on class and method.
  • @Action on method.

@Authorization replaces the whole authorization location. Blank values become null; they do not fall back to the route's original module, screen or action.

If @Authorization is present, it takes precedence over @Module, @Screen and @Action. Otherwise, Gate applies the partial overrides in the natural order package, class and method.

Responses

When access is denied, Gate distinguishes between missing identity and missing authorization.

  • 401 Unauthorized means there is no authenticated user.
  • 403 Forbidden means the user is authenticated, but the authorization check failed.
