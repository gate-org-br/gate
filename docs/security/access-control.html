Access Control

Gate has its own authorization model. It is more than a simple list of permissions on the user. Access may come from direct user entries, named function groups and the user's role in the role hierarchy.

Overview

The first idea to understand is this: Gate stores authorization data in its own database and uses that data when a route is executed.

Most routes use the default behavior. If you do not declare any special security annotation, Gate uses Security.Type.AUTHORIZATION. In this mode, once the framework resolves the route, it checks whether the current user has access to it.

That check is based on the authorization structure associated with the user. To understand the result, you need to understand four concepts: Auth, Role, Func and User.

Auth

An Auth is one access rule. It says whether something is granted or blocked, and to which part of the application that rule applies.

Every auth has two main characteristics:

  • Access: GRANT or BLOCK.
  • Scope: PUBLIC or PRIVATE.

GRANT means the auth gives access. BLOCK means the auth denies access.

PUBLIC and PRIVATE do not mean "public route" and "private route". They control how the auth behaves in the role hierarchy. A private auth stays on the role that owns it. A public auth may be inherited through parent roles.

An auth also has route fields: module, screen and action. These fields define what the rule applies to.

  • If only module is filled, the auth applies to the whole module.
  • If module and screen are filled, it applies to the whole screen.
  • If all three are filled, it applies to one specific action.
  • It may also use partial combinations such as module plus action.

So an auth does not always need to identify a single action. It can define access at a broader level.

Role

A Role is the user's place in the organizational structure. Roles are hierarchical: a role may have a parent role, and Gate uses that hierarchy when computing access.

A role may have its own auths and its own funcs. This means a role is not only a label such as "manager" or "operator". It is also a source of authorization data.

The public/private distinction matters here: role auths with scope PUBLIC may flow through the role hierarchy. Role auths with scope PRIVATE remain local to the role that owns them.

Func

A Func is a named group of auths.

In practical terms, a function lets you give a reusable name to a set of accesses. Instead of attaching the same auths one by one to many users or roles, you can attach a func and inherit its auths as a group.

A func may be attached to users and to roles. This makes funcs a reuse mechanism inside the authorization model.

User

A User may receive authorization data from more than one place.

  • The user's own direct auths.
  • The auths of the funcs attached directly to the user.
  • The auths of the user's role.
  • The auths of the funcs attached to the user's role.
  • Public auths inherited through the role hierarchy.

So the user's effective access is computed, not stored in one flat list. Gate combines those sources to decide whether the route is allowed.

How Gate Decides

When a route is executed in the default authorization mode, Gate follows this logic:

  1. Resolve the request to module, screen and action.
  2. Compute the user's effective auths from user, funcs and role.
  3. If any matching auth blocks the route, deny access.
  4. If nothing blocks and at least one matching auth grants the route, allow access.
  5. If there is no matching grant, deny access.

This is why the model is more sophisticated than it first appears. The answer does not come only from one permission directly attached to the user. It may come from any of the sources above.

Authorization Types

Gate supports both a general annotation and shortcut annotations.

Annotation Meaning
@Security(Security.Type.NONE) The route is open to everyone
@Security(Security.Type.AUTHENTICATION) The route requires an authenticated user
@Security(Security.Type.AUTHORIZATION) The route uses the normal authorization model
@Security(Security.Type.SPECIFIC_AUTHORIZATION) The route uses the overridden target defined by @Authorization
@Security(Security.Type.SUPERUSER) The route requires a superuser
@Security(Security.Type.BLOCK) The route is blocked for everyone
@Public Shortcut for Security.Type.NONE
@Superuser Shortcut for Security.Type.SUPERUSER
@Disabled Shortcut for Security.Type.BLOCK

These annotations may be declared on the package, on the screen class or on the action method. Method declarations override class declarations, and class declarations override package declarations.

Only one access type may be declared at the same level. For example, declaring @Public together with @Disabled on the same method is invalid. The same is true for mixing a shortcut annotation with @Security(...) on the same element.

Authorization Override

@Authorization is different from the other access annotations. It does not define the security type of the route. Instead, it changes which module, screen or action Gate should use during the authorization check.

This is useful when one route should be authorized as if it were another route. The executed action remains the same, but the permission check uses the overridden target.

This override may be declared on the package, on the screen class or on the action method, following the same precedence used by the rest of the framework.

Responses

When access is denied, Gate distinguishes between missing identity and missing authorization.

  • 401 Unauthorized means there is no authenticated user.
  • 403 Forbidden means the user is authenticated, but the authorization check failed.
