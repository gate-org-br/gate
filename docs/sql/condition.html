Condition

Use Condition for where, having, and join predicates. It is designed for the common DAO problem: keep the SQL readable while still adding optional filters and nested logic in Java.

Fixed SQL Expressions

Use literal SQL expressions when no bound parameter is needed.

Condition condition = Condition
	.of("User.active").isEq("true")
	.and("User.deletedAt").isNull();
Direct Parameters

This is the most common style in application code.

Condition condition = Condition.TRUE
	.and("User.name").lk(filter.getName())
	.and("User.active").eq(filter.getActive())
	.and("Department$id").eq(filter.getDepartmentId());
Property References

When the field belongs to a mapped Java type, you can use a property reference instead of a raw SQL column name. 

Condition condition = Condition.TRUE
	.and(User::getName).lk(filter.getName())
	.and(User::getActive).eq(filter.getActive());
Conditional Clauses

when(...) is the mechanism used by gate.sql to make a clause conditional without forcing you to branch the whole query in Java. Instead of writing multiple if/else blocks around the query, you keep one fluent expression and say that the next part of it should only exist when a runtime condition is true.

That is why when(...) reads naturally in search filters. A date range, an optional status, a user-specific restriction, or any other filter that may or may not exist can stay close to the clause it controls. This keeps the query readable, local, and easy to review, because the optional rule is expressed exactly where the SQL would appear.

When the assertion is true, the fluent chain continues normally and the next predicate is added to the SQL. When the assertion is false, that next predicate is skipped and the SQL remains unchanged. In other words, when(...) does not produce a different query object for you to manage separately; it keeps the same query flow and either lets the next clause in or quietly ignores it.

After when(...), the API starts offering supplier-based methods. That is not an implementation detail leaking by accident; it is there because the value of the next clause should be lazy as well. If a clause may disappear, the value associated with it should not be computed eagerly. This avoids work that will never be used and, more importantly, protects code that only makes sense inside the enabled branch.

That is why the idiomatic pattern after when(...) is to use the normal operator methods with supplier arguments, such as ge(...), lt(...), and the other supplier-based variants. They express two things at once: the clause is optional, and the value should only be obtained if the clause is really going to be part of the final SQL. 

Condition condition = Condition.TRUE
	.and("User.name").lk(filter.getName())
	.and().when(filter.getStartDate() != null).expression("User.createdAt")
		.ge(() -> filter.getStartDate().atStartOfDay())
	.and().when(filter.getEndDate() != null).expression("User.createdAt")
		.lt(() -> filter.getEndDate().plusDays(1).atStartOfDay());

If filter.getStartDate() is null, the lower-bound clause is not added and its supplier is never used. The same applies to the end date. The result is one query definition that stays linear and readable even when several filters are optional.

Nested Logic

Pass a condition into another condition when you need parentheses and explicit grouping. 

Condition condition = Condition
	.of("Supervisor.teamId").isEq("Shift.teamId")
	.and(Condition
		.of("Shift.userId").isEq("User.id")
		.or("User.active").eq(true));
EXISTS

Use exists(...) and not().exists(...) for subquery-based filtering and permission checks. 

Condition condition = Condition.TRUE
	.and().exists(Select.expression("id")
		.from("Share")
		.where(Condition.of("Share.User$id").eq(userId)))
	.and().not().exists(Select.expression("id")
		.from("BlockList")
		.where(Condition.of("BlockList.User$id").eq(userId)));
Main Methods
Method Use it for
of(...) Start a new predicate from a field, expression, or property reference
TRUE, FALSE Start composition from a neutral or always-false baseline
eq, ne, lt, le, gt, ge Compare with bound values
lk, rx, bw, in Use common SQL operators
isEq, isNe, isNull, isNotNull Compare with SQL expressions instead of bound values
and(...), or(...) Combine conditions and predicates, including property references
when(...) Add the next clause only if a runtime condition is true; after it, supplier-based methods become available for lazy values
exists(...) Attach an exists (subquery) predicate
not() Negate the next predicate or subquery
