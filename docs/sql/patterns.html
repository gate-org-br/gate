Production Patterns

This page consolidates robust patterns extracted from real DAO usage. The focus is on maintainability, safe writes, and predictable query behavior.

Dynamic Filter Baseline

Use Condition.TRUE to compose optional filters without special branching.

var condition = Condition.TRUE
	.and("User.name").lk(filter.getName())
	.and("User.username").eq(filter.getUsername())
	.and("Role.id").eq(filter.getRole().getId())
	.and().when(!getUser().isSuperUser()).expression("Access.id").isNotNull();

Why this pattern is good:

  • No duplicated query blocks
  • Optional filters remain local and readable
  • Works well with both raw SQL resources and builder queries
Access Rules with EXISTS

Use exists/not exists for permission and visibility logic.

Condition access = Condition
	.of("Ticket.confidential").isEq("false")
	.or("Ticket.requesterId").eq(getUser().getId())
	.or().exists(Select.expression("id").from("Share")
		.where(Condition.of("Ticket$id").isEq("Ticket.id")
			.and("Person$id").eq(getUser().getId())));

Condition c = Condition.TRUE.and(access);

Why this pattern is good:

  • Authorization rules stay in SQL, close to data filtering
  • Easy to extend with new OR branches
  • Avoids loading excess data and filtering in memory
Write Safety Guards

For updates/deletes, validate affected rows when the API expects an existing record.

if (Delete.from("Organization")
	.where(Condition.of("id").eq(value.getId()))
	.build()
	.connect(getLink())
	.execute() == 0)
	throw new NotFoundException();

Why this pattern is good:

  • Prevents silent no-op writes
  • Improves API semantics for callers
  • Detects race conditions early
Generated Key Strategies

Choose the generated key method by insert shape.

// single insert
Insert.into("Organization")
	.set("name", value.getName())
	.build().connect(getLink())
	.fetchGeneratedKey(ID.class)
	.ifPresent(value::setId);

// repeated or multi-key scenario
Insert.into("QuickMessage")
	.set("description", quickMessage.getDescription())
	.build().connect(getLink())
	.fetchGeneratedKeys(ID.class)
	.forEach(quickMessage::setId);

Why this pattern is good:

  • Makes identity handling explicit
  • Supports both simple and batched workflows
  • Prevents detached entities without IDs
Complex Optional Subfilters

Compose optional subqueries only when needed.

if (filter.getFeedback().getQuestion() != null
	|| filter.getFeedback().getText() != null)
	condition = condition.and().exists(Select
		.expression("id")
		.from("Feedback")
		.where(Condition.of("Feedback.Organization$id").isEq("Call.Organization$id")
			.and("Feedback.protocol").isEq("Call.protocol")
			.and("Feedback.question").eq(filter.getFeedback().getQuestion())
			.and("Feedback.text").eq(filter.getFeedback().getText())));

Why this pattern is good:

  • Avoids expensive subqueries when filters are empty
  • Keeps dynamic behavior explicit and testable
  • Maintains query readability under high complexity
