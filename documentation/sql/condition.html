Condition

Condition builds SQL predicates for where, having, and join clauses. In practice, DAO code uses three styles: no parameters, direct parameters, and placeholders resolved at execution.

No Parameters

Use literal SQL expressions when no bound values are needed.

Condition c = Condition
	.of("User.active").isEq("true")
	.and("deletedAt").isNull();

Output:

User.active = true and deletedAt is null
params: []
Direct Parameters

Most common style in DAOs: pass values while composing.

Condition c = Condition.TRUE
	.and("User.name").lk("Paul")
	.and("User.active").eq(true)
	.and("Department.id").eq(10);

Output:

0 = 0 and User.name like ? and User.active = ? and Department.id = ?
params: ["%Paul%", true, 10]
Null-Skipping Form Filters

To simplify search forms, eq, ne, and gt ignore null values. If a field is not filled, the predicate and parameter are not added. 

Filter filter = getFilterFromForm();

Condition c = Condition.TRUE
	.and("User.username").eq(filter.getUsername())
	.and("User.email").ne(filter.getExcludedEmail())
	.and("User.createdAt").gt(filter.getCreatedAfter());

Example behavior:

// if only username is filled
c.toString():
0 = 0 and User.username = ?

c.getParameters():
["paul"]
Execution-Time Parameters

Use placeholder methods like eq() and lk() when values will be provided during execution. 

Condition c = Condition
	.of("Department$id").eq()
	.and("name").lk()
	.and("createdAt").ge();

Query q = Select.expression("id")
	.from("User")
	.where(c)
	.build()
	.connect(getLink())
	.parameters(1, "Paul", LocalDate.now().minusDays(7));

Condition output before execution:

Department$id = ? and name like ? and createdAt >= ?
params: []
when(...) for Optional Filters

when(...) is heavily used in production DAOs to include predicates only when input is present. 

Condition c = Condition.TRUE
	.and("User.username").eq(filter.getUsername())
	.and().when(filter.getStartDate() != null).expression("Event.createdAt")
		.geGet(() -> filter.getStartDate().atStartOfDay())
	.and().when(filter.getEndDate() != null).expression("Event.createdAt")
		.ltGet(() -> filter.getEndDate().plusDays(1).atStartOfDay());

Why this is useful:

  • No duplicated query branches
  • Optional filter logic stays close to each predicate
  • Easy to combine with reusable baseline conditions
Field To Field and Nested Composition

Use isEq to compare field-to-field and pass conditions directly into and(Condition...). The nested call is parenthesized, which is the safe form. 

Condition c = Condition
	.of("Supervisor.teamId").isEq("Shift.teamId")
	.and(Condition
		.of("Shift.userId").isEq("User.id")
		.or("User.active").eq(true));

Output:

Supervisor.teamId = Shift.teamId
and (Shift.userId = User.id or User.active = ?)
params: [true]
EXISTS and NOT EXISTS

Use exists(Select...) with full subqueries. A common pattern is combining multiple alternatives with Condition.FALSE.or(). 

Condition c = Condition.TRUE
	.and(Condition.FALSE
		.or().exists(NEXT_RECEIVED_CONTACT)
		.or().exists(NEXT_MADE_CONTACT))
	.and().not().exists(Select.expression("id")
		.from("VisibilityException")
		.where(Condition.of("VisibilityException.contactId").isEq("Contact.id")));

Why this is useful:

  • Strong support for permission and visibility rules
  • Efficient filtering without materializing intermediate data
  • Expressive enough for complex business constraints
